# Native MCP management (F-024)

- Configuration belongs to the user (`agentDir/mcp-servers.json`) or one trusted project (`cwd/.pi/mcp-servers.json`). The versioned format is independent of Pi/Codex plugin manifests. Invalid files remain unchanged and report an error. Writes are atomic and serialized.
- Saving or enabling a server never starts it. Connect and Test are explicit user actions. Stdio uses an executable plus argument array with no shell; HTTP supports Streamable HTTP. OAuth/marketplace/config migration are outside this first version.
- Every connection belongs to a specific SDK session identity and workspace. Requests carry that identity; switching projects cannot adopt another owner's tools. Project configuration and connections require the SDK's project trust result. User configuration still needs explicit connection in each session.
- Credentials are references to named environment variables. Only variable names are saved or sent to the renderer, never resolved values. Stdio environment values and HTTP headers are resolved only when connecting. HTTP credentials are never followed to a redirected endpoint.
- Discovered tools use deterministic names containing a hash of server scope/id and the original tool name. This prevents collisions across servers; collisions with existing Pi tools are rejected. Pi's real extension API registers the schema and callable implementation, with active tools disabled immediately on disconnect. Every execution rechecks connection generation, server enabled state and the owner identity.
- Connect, discovery and calls have bounded timeouts and cancellation. Output, schemas, tool counts and configuration size are bounded. Tests initialize and discover tools then always disconnect without exposing them to the model. Failed MCP requests update that server's state without taking normal chat offline.
- Disconnect, disabled/deleted configuration, runtime disposal and app exit close the transport. Windows stdio teardown additionally terminates the owned process tree; no unrelated PID is targeted. Unexpected process exits remove active tools and report a recoverable error. No automatic reconnect or automatic process start is used.
- Acceptance uses actual local stdio and HTTP protocol servers, invokes a tool through the registered Pi adapter, exercises timeout/disconnect/disable/trust/scope/collision handling and checks owned PIDs exit. UI scenarios are prepared for the parent renderer runner; this stage does not launch user software.

## Verification record

`node --test tests/mcp-manager.test.mjs` passed 5 tests on Windows. It covers actual stdio request/response and process-tree teardown, local HTTP tool discovery/invocation with environment-variable header references, request cancellation, handshake timeout, immediate disconnect during a pending handshake, configuration disablement, untrusted project rejection, mismatched session/workspace identity, deterministic tool conflict rejection and disposal. The final test initializes the real AgentService/Pi SDK, invokes the discovered tool from `session.agent.state.tools`, then switches projects and verifies that the tool is absent there. No model request or external server is used.

Agent and UI TypeScript checks passed after implementation. Output is limited to 2 MiB, each discovered schema to 256 KiB, each server to 256 tools and each scope to 50 server configurations. Credentials must already exist as environment variables in the launched desktop process. HTTP supports Streamable HTTP only; OAuth and older HTTP+SSE transports are not implemented.

The independent headless renderer scenario `data-mcp.mjs` passed in `out/review/model-settings/runs/run-3uBkbw` with no runtime exceptions and no cleanup error. Recovery, connected MCP tools and the narrow configuration form were visually inspected from the three exported screenshots. These UI checks use fixture responses; protocol execution is covered separately by the real-server tests above.
